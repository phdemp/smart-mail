<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| classifier.js → thread.js → SQLite | fetchThreadContext reads emails table; must be user-scoped |
| router.js → llm_logs INSERT | Server-side write; userId from session, not from user-supplied input |
| opts.threadContext → LLM provider | Assembled prior messages flow through to the external API call |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-13 | Information Disclosure | classifier.js cross-user thread leakage | mitigate | fetchThreadContext receives userId from classifyEmail(userId, emailId) — userId is sourced from the authenticated session in the API route handler, not from request body. The V4 predicate in thread.js SQL ensures per-user scoping. |
| T-02-14 | Information Disclosure | llm_logs.user_id exposure | accept | llm_logs is server-side only in Phase 2; no API endpoint reads it. Phase 4 will add GET /api/llm/health with auth guard. The table contains no email content — only metadata (provider, outcome, token count). |
| T-02-15 | Denial of Service | fetchThreadContext failure in classify hot path | mitigate | fetchThreadContext is wrapped in IIFE try/catch that returns []; buildThreadContext([]) returns null; threadContext = null || undefined = undefined; base.js skips injection when threadContext is absent. Thread context errors degrade gracefully to single-email classify. |
| T-02-16 | Spoofing | tokenCount as API cost estimate | accept | tokenCount is a chars÷4 proxy per D-04 — it is an estimate, not an exact count. It is logged for observability (Phase 4 cost analysis), not used for billing or security decisions. Under-counting is acceptable; the 6000-char budget cap on buildThreadContext bounds the maximum estimate. |
</threat_model>
