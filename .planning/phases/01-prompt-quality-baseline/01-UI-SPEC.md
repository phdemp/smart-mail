# Phase 1 — UI Design Contract

> Visual and interaction contract for Phase 1: Prompt Quality Baseline.
> Generated by gsd-ui-researcher. Covers exactly two new UI states introduced
> by D-20 (source='failed') and D-10 ("Generating…" state). All other UI
> elements are inherited from the existing design system unchanged.

## Scope Note

Phase 1 is a backend-heavy phase. Only two UI surfaces change:

1. **Classification-failed badge** — displayed in the email list row and email
   detail header when `source = 'failed'` (INFRA-02).
2. **Draft-generating state** — displayed in the draft editor when the Reply
   button has been pressed and `router.generateDraft()` is in flight (D-10).

No layout changes. No new pages. No new components beyond what is specified here.

## New UI Contracts — Phase 1

### Contract A: Classification-Failed Badge

**Trigger condition:** `classifications.source = 'failed'` — email exhausted 3
classification attempts with no valid LLM response.

**Placement:** Same slot as existing category badges. Replaces the category
badge entirely when `source = 'failed'`. Appears in:
- Email list row (center panel) — in the badge row alongside urgency and star.
- Email detail header (right panel) — in the badge strip next to the subject.

**Visual specification:**

```
CSS class: badge badge-failed
```

```css
.badge-failed {
  background: rgba(239, 68, 68, 0.15);
  color: #ef4444;
  border: 1px solid rgba(239, 68, 68, 0.3);
}
```

- Inherits all `.badge` base properties: IBM Plex Mono, 10px, weight 600,
  padding 2px 8px, border-radius 100px, letter-spacing 0.05em, text-transform
  uppercase, white-space nowrap, display inline-flex.
- No animation. Static badge — failure is a terminal state.
- Label text: `FAILED`

**Color rationale:** Reuses `--accent-red` / `#ef4444` — the same token already
used for `badge-legal` and urgency-urgent. Consistent with the existing error
severity tier. User confirmed this choice.

**Server-side rendering:** In `src/routes/api.js`, the email list row renderer
and email detail renderer both call `categoryLabel(cat)` and emit
`class="badge badge-${cat}"`. When `source = 'failed'`, emit
`class="badge badge-failed"` with label `FAILED` regardless of the `cat`
column value. The condition to check is `cls?.source === 'failed'`, not the
category column.

**Empty state for classification:** When `source = 'failed'`, the AI Draft
Response section remains visible (the placeholder draft row still exists with
`body = ''`). The draft textarea shows the fallback copy from DEFAULTS
(`draft_reply`). The FAILED badge communicates that classification metadata
(category, urgency, summary) could not be determined — not that the email is
broken.

**No tooltip required** in Phase 1. The badge label alone is sufficient signal.
Tooltip text can be added in Phase 5 (UI polish).

### Contract B: Draft-Generating State

**Trigger condition:** User clicks Reply (which fires
`POST /api/emails/:id/draft/regen`). The `router.generateDraft()` call is in
flight. Duration: typically 1–4 seconds.

**Placement:** Inside the existing `.draft-editor` component, above the
`<textarea>`.

**Visual specification — label:**

```
Element: <span> above textarea, replaces "AI Draft Response" heading during generation
Text: "Generating draft…"
Font: IBM Plex Mono, 10px, weight 600, text-transform uppercase,
      letter-spacing 0.08em, color var(--text-muted)
Animation: pulse-pending (already defined in app.css)
```

The label inherits `.badge-pending` animation: opacity cycles 1 → 0.4 → 1 over
1.5 s ease-in-out infinite. Apply animation only to the label span — not to
the textarea or the surrounding container.

```html
<!-- State: generating (x-show="generating") -->
<span class="badge badge-pending" style="margin-bottom:8px;display:inline-block;">
  Generating draft…
</span>
```

**Visual specification — textarea:**

During generation, the textarea is visible but non-interactive:

```
disabled attribute: true
background: var(--bg-raised)   (same as normal — no additional dimming)
opacity: 0.5
cursor: default
```

No spinner overlay. No skeleton shimmer. The pulsing label above the textarea
is the sole loading indicator.

**State transition (Alpine.js):**

The existing `draftEditor()` Alpine component already has a `regenerating`
boolean. Extend it with a `generating` boolean for the initial Reply flow
(distinct from Regen, which has its own `regenerating` state):

- `generating = false` — default; textarea is enabled, label reads "AI Draft Response"
- `generating = true` — set when Reply is clicked; textarea disabled at 0.5 opacity;
  label switches to pulsing "Generating draft…" badge
- On API response (success): `generating = false`; textarea re-enabled; body
  populated with returned `draft_reply`
- On API error: `generating = false`; textarea re-enabled; body retains
  DEFAULTS fallback text; error toast shown (see Copywriting Contract below)

**Existing Regen button state is unchanged.** The `regenerating` boolean and
`↻ Regen` / `...` swap continue to work as before for the Regen button. The
new `generating` state only applies to the initial on-demand generation when
the Reply button triggers the first real draft call.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Classification-failed badge | `FAILED` |
| Draft generating label | `Generating draft…` |
| Draft error toast (generation failed) | `Draft generation failed. Try Regen or write manually.` |
| Draft section heading (normal state) | `— AI Draft Response —` (existing, unchanged) |
| Empty state heading (no email selected) | `Select an email to read` (existing, unchanged) |
| Empty state body | `IntelliMail classifies every email using Claude AI — meeting requests, financials, legal notices, travel, and more.` (existing, unchanged) |

No destructive actions are introduced in Phase 1. No confirmation dialogs
required.

Error state copy rule: always state the problem and the action available.
"Draft generation failed." = problem. "Try Regen or write manually." = next
step. Both parts are mandatory.

## Implementation Notes for Executor

1. Add `.badge-failed` to `public/css/app.css` immediately after `.badge-other`
   (line 312). No new keyframes needed — static badge.

2. In `src/routes/api.js`, in the email list row renderer (around line 389) and
   the email detail header renderer (around line 491), add a guard before
   emitting the category badge:

   ```javascript
   const badgeCat = cls?.source === 'failed' ? 'failed' : cat;
   const badgeLabel = cls?.source === 'failed' ? 'FAILED' : categoryLabel(cat);
   // then emit: <span class="badge badge-${badgeCat}">${badgeLabel}</span>
   ```

3. In the `draftEditor()` Alpine component, add `generating: false` to the
   data object. Set `generating = true` before the fetch call for on-demand
   draft generation, and reset it in both `.then()` and `.catch()` branches.

4. In the draft editor template (dashboard.html or server-rendered HTML in
   api.js around line 556), add the conditional label above the textarea:

   ```html
   <template x-if="generating">
     <span class="badge badge-pending" style="margin-bottom:8px;display:inline-block;">
       Generating draft…
     </span>
   </template>
   <textarea x-model="draftBody" @input="debouncedSave()" rows="8"
             :disabled="generating"
             :style="generating ? 'opacity:0.5;cursor:default;' : ''">
   </textarea>
   ```

5. Error toast on draft generation failure uses the existing `showToast()`
   utility: `showToast('error', 'Draft generation failed. Try Regen or write manually.')`.
